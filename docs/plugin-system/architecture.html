1. What the plugin system does

AntennaPod can be extended by plugins that are separate Android apps — each with its own APK, its own repository, and its own process. After an episode finishes downloading, AntennaPod hands the audio to any enabled plugin, which can return a transcript or chapter markers. The result is applied through AntennaPod's existing transcript/chapter pipelines, so plugin-generated content is indistinguishable from publisher-provided content.

Crucially, no plugin code ever runs inside AntennaPod's process. Plugins are discovered on the device and driven over Android's binder IPC. They are disabled by default and only run after the user enables them in Settings → Plugins.

2. Design goals & constraints

Hard constraints

  • Google Play policy. Apps may not download and execute code that changes app behaviour. This rules out any form of dynamic code loading.
  • Privacy. AntennaPod is FOSS and privacy-first. Uploading users' audio to a cloud service by default is unacceptable.
  • Stability. A misbehaving third-party plugin must not be able to crash the podcast player.

Desirable properties

  • Independent lifecycle. Plugins should install, update, and version on their own, without an AntennaPod release.
  • Least privilege. A plugin should see only the one audio file it is asked to process — never AntennaPod's database or private files.
  • Small, stable seam. The existing download pipeline should call plugins through a single unchanged in-process interface.
  • Capability negotiation. A plugin advertises what it can do; the host only asks for what is missing.

3. The current implementation chosen

Plugins are implemented as out-of-process AIDL bound services. Three Gradle modules divide the responsibility:

:app
Declares the PLUGIN permission & <queries> entry · registers discovery in ClientConfigurator · PluginsPreferencesFragment (enable/disable) · PluginDebugOverlay
▲ depends on
:plugin:host  — the plugin SDK
AIDL IMediaProcessorPlugin + PluginMediaRequest/PluginMediaResult/PluginChapter parcelables + PluginContract · PluginManager (discovery + live re-sync) · RemoteMediaProcessor (bind, invoke, apply) · PluginPreferences · PluginDescriptor
▲ depends on
:plugin:api  — the internal seam
DownloadedMediaProcessor interface · MediaProcessorRegistry · PluginDebugLog  — depended on by the download pipeline (:net:download:service)

The seam is deliberately tiny. The download pipeline knows nothing about plugins, AIDL, or binders — it only calls MediaProcessorRegistry.runAll() against the DownloadedMediaProcessor interface: 

public interface DownloadedMediaProcessor {
    String getId();
    boolean shouldProcess(FeedMedia media);
    void process(Context context, FeedMedia media);
}

Each discovered plugin is wrapped in a RemoteMediaProcessor (which implements that interface) and registered. This is the single in-process integration point; everything cross-process lives behind it.

Discovery

PluginManager.discover() asks PackageManager.queryIntentServices() for every service that responds to the action de.danoeh.antennapod.plugin.action.MEDIA_PROCESSOR, reading each service's <meta-data> for a plugin ID and a capability bitmask. A BroadcastReceiver on PACKAGE_ADDED/REMOVED/REPLACED re-syncs the registry live, so installing a plugin makes it appear without restarting AntennaPod. On Android 11+ a <queries> element is required for the host to even see plugin packages.

4. The cross-process contract

The AIDL interface is intentionally minimal:

interface IMediaProcessorPlugin {
    String getPluginId();
    int getCapabilities();
    PluginMediaResult process(in PluginMediaRequest request);
}

Request → plugin

PluginMediaRequest carries:

  • capability — which single capability to run
  • mediaFd — the audio as a read-only ParcelFileDescriptor
  • mimeType, episodeTitle, durationMs

Passing a file descriptor — not the bytes — sidesteps the ~1 MB binder transaction limit and grants access to exactly one file.

Result ← plugin

PluginMediaResult carries:

  • success, resultType (NONE/TRANSCRIPT/CHAPTERS)
  • content + contentMimeType (transcript)
  • chapters — list of PluginChapter (startMs, title, url, imageUrl)

Capabilities are a bitmask: TRANSCRIPTION = 1, CHAPTERS = 1 << 1.

5. End-to-end flow

Plugins run when an episode finishes downloading — not at app launch. At launch, only discovery and registration happen. 
Download completes
   └─ MediaDownloadedHandler
        └─ MediaProcessorRegistry.runAll(context, media)
             └─ for each registered processor:
                  RemoteMediaProcessor.shouldProcess(media)?   // enabled? local audio? content missing?
                     └─ RemoteMediaProcessor.process(...)
                          1. bindService(BIND_AUTO_CREATE)      // 15s timeout, CountDownLatch
                          2. IMediaProcessorPlugin.process(request)   // audio passed as read-only FD
                          3. apply result:
                               transcript → TranscriptUtils.storeTranscript + item.setTranscriptUrl
                               chapters   → item.setChapters
                             → DBWriter.setFeedItem(...)         // existing pipelines
                          4. unbindService()  (finally)

shouldProcess() gates work three ways: the plugin must be enabled, the media must be local audio, and the episode must actually be missing the content the plugin would provide (no existing transcript / no existing chapters). Only the applicable capabilities are invoked.

6. Security & isolation model

  • Process isolation — a plugin runs in its own process; a crash or hang cannot take down the player (binding uses a timeout).
  • No dynamic code loading — AntennaPod never loads plugin code; it only sends a binder message. Play-policy compliant.
  • Least-privilege data access — the plugin receives one read-only file descriptor, never AntennaPod's database or private storage.
  • Custom permission — de.danoeh.antennapod.permission.PLUGIN (protectionLevel="normal") gates who may bind.
  • Explicit opt-in — plugins are disabled by default and enabled per-plugin by the user.
  • Auditable output — results flow through the same transcript/chapter code paths as normal content, with no special privileges.

7. Debug tooling

Because the interesting behaviour happens across a process boundary on a background thread, the system ships an observability layer: PluginDebugLog (a live, in-memory ring buffer in :plugin:api, also mirrored to logcat) records every discovery, enablement check, bind, request, result, and apply step. A draggable floating PluginDebugOverlay — toggled from Settings → Plugins → Show debug overlay — renders those events in real time on top of the app.

8. Alternative architectures considered

A. Out-of-process AIDL bound services  chosen

Plugins are separate apps; the host binds their service and drives it over binder IPC. (Described in detail above.)

Pros
  • Strong process & permission isolation
  • No dynamic code loading — Play compliant
  • Independent install/update per plugin
  • Large data via FD, not marshalled bytes
  • Explicit capability negotiation
Cons
  • AIDL + parcelable boilerplate
  • IPC/binding overhead & a timeout to manage
  • User must install each plugin as a full app
  • Package-visibility (<queries>) needed on Android 11+

B. In-process dynamic code loading (DexClassLoader / plugin JARs)

Load plugin classes into AntennaPod's own process and call them directly.

Pros
  • Fastest — no IPC, direct object calls
  • Trivial data passing (shared references)
  • Single process, single install
Cons
  • Violates Google Play policy on executable code
  • Plugin inherits all of AntennaPod's permissions & data
  • A plugin crash crashes the whole app
  • No sandbox; serious supply-chain risk
  • ABI/versioning fragility

C. Cloud / REST web service

Upload the audio to a remote server that returns transcripts/chapters.

Pros
  • Heavy ML models run server-side
  • No on-device compute or model shipping
  • Logic updated centrally, cross-platform
Cons
  • Privacy — sends user audio to a third party
  • Requires network, bandwidth, and money
  • No offline support; added latency
  • Against AntennaPod's FOSS/privacy ethos
  • Not really an on-device "plugin" ecosystem

D. Broadcast / implicit-Intent (fire-and-forget)

Broadcast an intent describing the media; plugins reply via another intent.

Pros
  • Very loose coupling, minimal contract
  • Familiar Android primitive
Cons
  • No natural synchronous request/response
  • Modern background-execution & implicit-broadcast limits
  • Awkward, insecure large-data handoff
  • No clean capability negotiation or lifecycle

E. ContentProvider-based

Each plugin exposes a ContentProvider; the host queries it and reads results via openFile.

Pros
  • Standard IPC with a permission model
  • Streaming via openFile
  • Process isolation like the chosen design
Cons
  • CRUD semantics fit "process & return" poorly
  • No natural "run this, then call back" model
  • Capability discovery must be bolted on
  • More ceremony for the same isolation AIDL already gives

F. Embedded scripting / WASM sandbox

Plugins are scripts (JS/Lua/WASM) interpreted by a sandbox inside the app.

Pros
  • No separate app to install
  • Portable, hot-loadable plugin scripts
Cons
  • Grey area vs. Play's dynamic-code rules
  • Must build & secure a whole runtime/sandbox
  • Hard to reach native audio/ML libraries
  • Large engineering effort for little gain here

G. Compile-time bundled Gradle modules

Each "plugin" is a module compiled into the AntennaPod APK — the pattern AntennaPod already uses for features.

Pros
  • Simplest possible; fully trusted, type-safe
  • No IPC, no discovery, no permissions
Cons
  • Not a third-party ecosystem — every plugin must be merged & shipped
  • Bloats the app; no independent updates
  • Not user-installable; gated on AntennaPod releases

10. Why AIDL bound services won

Only two constraints are truly non-negotiable for AntennaPod: Google Play compliance and user privacy. Those immediately eliminate dynamic code loading (B) and a default cloud service (C). Of the remaining Play-safe, on-device, isolated options, the differentiator is fit for a synchronous "process this file and return structured data" interaction:

  • Broadcasts (D) give no clean way to return a result and fight modern background limits.
  • ContentProviders (E) force request/response into CRUD queries.
  • A scripting/WASM sandbox (F) is a large, security-sensitive engineering project for no additional benefit here.
  • Bundled modules (G) are trivial but are not a third-party, independently-updatable ecosystem at all.

AIDL bound services (A) are the one option that satisfies every hard constraint and models the interaction natively: a typed process(request) → result call, real process isolation, a file-descriptor handoff that respects the binder size limit and grants least-privilege access, and plugins that ship and update as ordinary Android apps. The cost — some AIDL boilerplate and a bound-service lifecycle to manage — is modest and fully contained behind the one-method DownloadedMediaProcessor seam.
