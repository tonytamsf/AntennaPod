Overview

Plugins are separate Android apps

Each plugin is its own APK, its own repo, its own process. AntennaPod discovers installed plugin apps on-device via PackageManager and drives them over Android's binder IPC. No plugin code ever runs inside AntennaPod's process. Plugins are disabled by default and only execute after the user toggles them on in Settings → Plugins.

Plugin-generated content — transcripts and chapter markers — flows through AntennaPod's existing transcript and chapter pipelines, so it is indistinguishable from publisher-provided content.

Key design constraint: Google Play policy prohibits downloading and executing code that changes app behavior. This rules out any form of dynamic code loading, making out-of-process AIDL the natural choice for an on-device plugin ecosystem.
Module Architecture

Three modules, one seam

The download pipeline knows nothing about plugins, AIDL, or binders. It only calls MediaProcessorRegistry.runAll() against a list of DownloadedMediaProcessor implementations. Everything cross-process lives behind that one interface.

The seam interface is intentionally tiny:

public interface DownloadedMediaProcessor {
    String getId();
    boolean shouldProcess(FeedMedia media);
    void process(Context context, FeedMedia media);
}

Each discovered plugin is wrapped in a RemoteMediaProcessor (which implements this interface) and registered. This is the single integration point.

IPC Contract

The cross-process AIDL interface

interface IMediaProcessorPlugin {
    String getPluginId();
    int getCapabilities();
    PluginMediaResult process(in PluginMediaRequest request);
}

Request → Plugin

PluginMediaRequest

  • capability — which single capability to run
  • mediaFd — audio as a read-only ParcelFileDescriptor
  • mimeType · episodeTitle · durationMs
binder IPC ↔

Result ← Plugin

PluginMediaResult

  • success · resultType (NONE / TRANSCRIPT / CHAPTERS)
  • content + contentMimeType (transcript text)
  • chapters — list of PluginChapter

Passing a file descriptor — not the bytes — sidesteps the ~1 MB binder transaction limit and grants access to exactly one file. The plugin never sees AntennaPod's database or private storage.

Capabilities

Advertised as a bitmask in <meta-data> on each plugin's manifest service entry:

TRANSCRIPTION 0x1 CHAPTERS 0x2 EPISODE_RETENTION separate AIDL

The host only invokes capabilities the episode is missing — if it already has a transcript, the transcription capability is skipped.

Discovery

How plugins are found

PluginManager.discover() uses PackageManager.queryIntentServices() to find every service responding to the action de.danoeh.antennapod.plugin.action.MEDIA_PROCESSOR. Each service's <meta-data> declares a plugin ID and capability bitmask.

A BroadcastReceiver on PACKAGE_ADDED / REMOVED / REPLACED re-syncs the registry live — installing or removing a plugin app takes effect without restarting AntennaPod.

Plugin manifest declaration

<service
    android:name=".TranscriptionPluginService"
    android:exported="true"
    android:permission="de.danoeh.antennapod.permission.PLUGIN">
    <intent-filter>
        <action android:name="de.danoeh.antennapod.plugin.action.MEDIA_PROCESSOR"/>
    </intent-filter>
    <meta-data android:name="de.danoeh.antennapod.plugin.ID"
               android:value="sample-transcription"/>
    <meta-data android:name="de.danoeh.antennapod.plugin.CAPABILITIES"
               android:value="3"/>  <!-- TRANSCRIPTION | CHAPTERS -->
</service>
Security

Isolation & trust model

🔒
Process isolation
Plugin runs in its own process. A crash or hang cannot take down the podcast player — binding uses a 15-second timeout.
🛡
No dynamic code loading
AntennaPod never loads plugin code. It sends a binder message. Fully Google Play policy compliant.
📁
Least-privilege data
Plugin receives one read-only file descriptor — never AntennaPod's database, preferences, or private storage.
🔑
Custom permission
de.danoeh.antennapod.permission.PLUGIN with protectionLevel="normal" gates who may bind.
✅
Explicit opt-in
Disabled by default. Each plugin must be individually enabled by the user in Settings → Plugins.
🔍
Auditable output
Results flow through the same transcript/chapter code paths as normal content, with no special privileges.
Observability

Debug tooling

Because the interesting behavior happens across a process boundary on a background thread, the system ships an observability layer:

PluginDebugLog

A live, in-memory ring buffer in :plugin:api that records every discovery, enablement check, bind, request, result, and apply step. Mirrored to logcat.

PluginDebugOverlay

A draggable floating overlay — toggled from Settings → Plugins → Show debug overlay — that renders PluginDebugLog events in real time on top of the app. Color-coded by severity. Requires SYSTEM_ALERT_WINDOW.

Decision Record

Alternatives considered

A. Out-of-process AIDL bound services Chosen

Plugins are separate apps; the host binds their service and drives it over binder IPC.

Strengths
  • Strong process & permission isolation
  • No dynamic code loading — Play compliant
  • Independent install/update per plugin
  • Large data via FD, not marshalled bytes
  • Explicit capability negotiation
Trade-offs
  • AIDL + parcelable boilerplate
  • IPC overhead & binding timeout to manage
  • User installs each plugin as a full app
  • <queries> needed on Android 11+

B. In-process dynamic code loading

Load plugin classes into AntennaPod's own process via DexClassLoader.

Strengths
  • Fastest — no IPC, direct object calls
  • Trivial data passing
Trade-offs
  • Violates Google Play policy
  • Plugin inherits all app permissions & data
  • A plugin crash crashes the whole app

C. Cloud / REST web service

Upload audio to a remote server that returns transcripts/chapters.

Strengths
  • Heavy ML models run server-side
  • Cross-platform, centrally updated
Trade-offs
  • Sends user audio to a third party
  • Against AntennaPod's FOSS/privacy ethos
  • Requires network + money

D. Broadcast / implicit-Intent

Broadcast an intent describing the media; plugins reply via another intent.

Strengths
  • Very loose coupling
  • Familiar Android primitive
Trade-offs
  • No synchronous request/response
  • Modern background-execution limits
  • Awkward large-data handoff

E. ContentProvider-based

Each plugin exposes a ContentProvider; host queries it and reads results via openFile.

Strengths
  • Standard IPC with permission model
  • Process isolation
Trade-offs
  • CRUD semantics fit "process & return" poorly
  • Capability discovery must be bolted on

F. Embedded scripting / WASM sandbox

Plugins are scripts interpreted by a sandbox inside the app.

Strengths
  • No separate app to install
  • Portable, hot-loadable
Trade-offs
  • Grey area vs Play's dynamic-code rules
  • Must build & secure a whole runtime
  • Hard to reach native audio/ML libraries

G. Compile-time bundled Gradle modules

Each "plugin" is a module compiled into the AntennaPod APK.

Strengths
  • Simplest possible; fully trusted
  • No IPC, no discovery
Trade-offs
  • Not a third-party ecosystem
  • Bloats the app; no independent updates

Rationale

Why AIDL bound services won

Two constraints are truly non-negotiable: Google Play compliance and user privacy. These immediately eliminate dynamic code loading (B) and a default cloud service (C).

Of the remaining Play-safe, on-device, isolated options:

  • Broadcasts (D) give no clean way to return a result and fight modern background limits.
  • ContentProviders (E) force request/response into CRUD queries.
  • Scripting/WASM (F) is a large, security-sensitive engineering project for no additional benefit.
  • Bundled modules (G) are trivial but are not a third-party ecosystem at all.

AIDL (A) is the one option satisfying every hard constraint and modeling the interaction natively: a typed process(request) → result call, real process isolation, a file-descriptor handoff that respects the binder size limit, and plugins that ship as ordinary Android apps. The cost — AIDL boilerplate and a bound-service lifecycle — is modest and fully contained behind the one-method DownloadedMediaProcessor seam.

Extension

Episode retention: a second plugin capability

Beyond media processing, the system extends to a second AIDL contract for episode retention (AntennaPod issue #2077). A retention plugin implements IEpisodeRetentionPlugin with a selectForDeletion() method.

EpisodeRetentionManager discovers retention plugin services, groups a feed's downloaded episodes, asks the enabled plugin which to delete, and deletes them with hard host-side guards: only downloaded, non-favorite, non-queued, non-local episodes can be removed.

Retention runs after auto-download via AutoDownloadManagerImpl, using the same disabled-by-default, per-plugin-enablement model.
