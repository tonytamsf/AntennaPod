AntennaPod  Plugin System

Extension Roadmap

Which long-standing upstream feature requests the out-of-process plugin architecture should absorb, which plugin entry points have to exist before that is possible, and which plugins should be written against them.

Companion document. This builds on Plugin System Architecture, which describes the design as shipped in PR #14: plugins are separate Android apps, discovered via PackageManager, driven over an AIDL bound service, disabled by default, and wired into the download pipeline through MediaProcessorRegistry. That document answers how plugins work. This one answers what they should be used for next.

1. Method & issue snapshot

The candidate set is every open issue in AntennaPod/AntennaPod labelled Type: Feature request, taken twice: the 40 most-commented and the 40 oldest. The two lists overlap by 19 issues, giving 61 distinct requests. Snapshot taken 2026-07-31; comment counts drift, so treat them as a ranking signal, not a fact about today.

Each request was given one of three verdicts:

  • Plugin — the feature can live almost entirely in a plugin app. Core's job is to add an entry point and get out of the way. These are typically features that were declined or stalled on scope grounds, need a dependency core does not want, or serve a minority of users at a cost the whole user base would otherwise pay.
  • Hybrid — the data can come from a plugin, but the application and UI must stay in core. Splitting it this way is what makes the feature affordable; keeping both halves in a plugin would fragment behaviour.
  • Core — a plugin API does not help. Usually because the request is a policy/UX decision over data structures core owns (queue, inbox, auto-download), or a UI change. Adding an extension point here would export a design argument to third parties rather than settle it.

14 of 61 requests came out as Plugin or Hybrid. That ratio matters: the plugin system is not a way to clear the backlog. It is a way to unblock the specific requests that are stuck precisely because they do not belong in the core APK.

2. Headline recommendation

#4159 — Introduce SponsorBlock to allow blocking/skipping audio ads  flagship

Opened 2020-05-16 · 20 comments · labelled Needs: Decision

This is the request the plugin architecture is most clearly the answer to, for one reason above all: it has already been rejected once on scope grounds. Its predecessor (#3382) was declined because running an ad-detection service is not something AntennaPod wants to own. #4159 tried to route around that by proposing an existing third-party database — which trades a maintenance objection for a privacy objection, since matching episodes against a remote service means telling that service what the user listens to. Six years later it is still labelled Needs: Decision.

Every horn of that dilemma is dissolved by putting it in a plugin app:

  • Nobody is asked to own it. The database integration, its terms, and its uptime live in a repo that is not AntennaPod's.
  • The privacy objection becomes an install-time choice. Core makes no network call; a user who never installs the plugin has no new exposure, and the default for everyone else is off.
  • The decision stops being binary. Maintainers can ship the entry point without endorsing any particular segment database — including community, offline, or on-device detectors.
  • It fits the existing shape. "Analyse an episode, return structured time-coded data, apply it through an existing pipeline" is exactly what PR #14 already does for chapters.

It also pays for itself twice: the segment model it needs is the same one #5924 (mark chapters for skipping) needs for user-marked segments. Build it once, and the plugin and the user are two sources feeding one feature.

Required: E1 (segment provider), ideally with E3 (metadata-time trigger) and E0 (async results). Delivered by P1.

Runner-up: #4671 — Support for podcast:value

Opened 2020-11-08 · 32 comments · labelled Needs: Decision, Area: Podcast Index / Podcasting 2.0

Value-for-value payments require AntennaPod to become a Lightning wallet — the issue itself lists "wallet functionality" and "set up a Lightning Node" as prerequisites and concedes "it's BIG". A podcast player should not ship a cryptocurrency wallet, hold user funds, or take on the store-policy and key-custody surface that comes with one; a plugin app can do all three without implicating the core APK, and users who do not want it never install it. Ranked second only because it needs more new contract surface than #4159 (E7 + E8), and because core must first stop discarding the podcast:value tag at parse time.

4. What PR #14 covers, and where it stops

PR #14 establishes one trigger, one direction of data flow, and two capabilities: 

trigger      MediaDownloadedHandler        // exactly one: after a successful download
transport    IMediaProcessorPlugin.process(PluginMediaRequest) -> PluginMediaResult
input        read-only ParcelFileDescriptor + title, mimeType, durationMs
output       transcript String | List<PluginChapter>
capabilities CAPABILITY_TRANSCRIPTION = 1, CAPABILITY_CHAPTERS = 1 << 1

That shape has four consequences, and every proposal below is a response to one of them:

Downloaded episodes only

A plugin is never consulted for a streamed episode, and never again after the first download. Anything that should also work while streaming, or should refresh when the publisher edits the feed (#4212), needs a second trigger → E3.

Two result types

resultType is TRANSCRIPT or CHAPTERS. Time-coded segments, loudness measurements, and search results have no representation → E1, E2, E4.

Download pipeline only

The single in-process seam is MediaProcessorRegistry, reached from the downloader. Playback, discovery, and sync each have their own seams (PlaybackServiceMediaPlayer, PodcastSearcherRegistry, SynchronizationProvider) that no plugin can reach → E4, E5, E6, E8.

One synchronous call, no UI

process() blocks a download worker thread, and a plugin cannot contribute anything a user can see or tap beyond an on/off switch. Speech-to-text, loudness scans, and QR capture all need more than that → E0, E4, E7.

5. Proposed entry points

Sketches are illustrative, not final API. Names follow the existing de.danoeh.antennapod.plugin.host conventions.

E0 — Contract hardening prerequisite

Unblocks: everything below · Motivating issues: none directly

Five gaps in the current contract get worse with every capability added, and are far cheaper to fix before there is an ecosystem than after:

  • Asynchronous results. process() is a blocking binder call on a download worker with a bind timeout. Speech-to-text (P5) and a loudness scan (P3) run for minutes. Add process(in PluginMediaRequest request, in IPluginResultCallback callback) as a oneway call, and have the host run plugin work in its own WorkManager job with progress and cancellation.
  • Payloads over the binder limit. PluginMediaResult.content is a String. A long transcript with speaker labels can approach the ~1 MB binder transaction ceiling, where it fails as a TransactionTooLargeException rather than degrading. Results should be returned the same way inputs already are — as a ParcelFileDescriptor — with the inline string kept only for small payloads.
  • Contract versioning. Add getContractVersion() and a META_DATA_CONTRACT_VERSION, and have PluginManager refuse to register a plugin built against an incompatible major. Today an old plugin meeting a new host fails at an arbitrary point instead of at discovery.
  • Provenance. Plugin output is deliberately indistinguishable from publisher content — good for pipeline reuse, bad for trust and cleanup. Record the producing plugin id alongside generated transcripts/chapters so the UI can say "chapters generated by X" and so uninstalling a plugin can offer to drop what it produced.
  • Declared side effects. A capability says what a plugin produces, not what it costs. Add META_DATA_USES_NETWORK / META_DATA_USES_REMOTE_SERVICE so Settings → Plugins can warn before the user enables something that will talk to a server about their listening — the exact concern that has kept #4159 unresolved.

E1 — Segment provider highest value

Motivating issues: #4159, #5924 · Delivered by P1

A plugin returns time ranges within an episode, each with a category and a suggested action. Core owns what happens to them. 

parcelable PluginSegment {
    long startMs; long endMs;
    int category;      // SPONSOR | SELF_PROMO | INTRO | OUTRO | MUSIC | OTHER
    int action;        // SKIP | MUTE | MARK_ONLY
    float confidence;  // 0..1
    String label;
}
// PluginContract
CAPABILITY_SEGMENTS  = 1 << 2;
RESULT_TYPE_SEGMENTS = 3;

Core-side work. Persist segments per FeedMedia; have :playback:service consult them on position updates (the same place chapter transitions are already noticed) and skip or mute; show them on the player screen so a skip is visible and undoable. That UI is also where #5924 lands — user-marked segments and plugin-supplied segments are the same record with a different source.

Two-way, opt-in. Community databases need contributions. Add submitSegments(in PluginSegmentSubmission s) as a separate oneway method behind its own consent toggle, so "use the database" and "send data to the database" are distinct decisions.

Depends on E3 for streamed episodes and for lookups that need no audio.

E2 — Offline audio analysis → playback profile

Motivating issue: #2187 · Delivered by P3

Loudness normalization splits cleanly: measuring is expensive, opinionated, and perfectly suited to a plugin; applying is a few lines in the existing ExoPlayer pipeline. A plugin scans the downloaded file once and returns a profile; core applies it as a gain on playback. 

parcelable PluginLoudnessProfile {
    float integratedLufs;     // EBU R128
    float truePeakDb;
    float suggestedGainDb;    // what core applies
    float loudnessRangeLu;    // optional, for dynamics decisions
}
CAPABILITY_LOUDNESS_ANALYSIS = 1 << 3;
Explicit non-goal: real-time DSP over the binder. Streaming PCM frames to another process and back cannot meet audio latency requirements and would burn battery for the entire duration of playback. Anything that must touch the sample stream continuously — a true compressor/limiter, smoother skip-silence (#4229), a rewind beep (#8078) — stays an in-process ExoPlayer AudioProcessor in core. The plugin boundary is the right place for analysis, not for the audio path.

E3 — Metadata-time trigger

Motivating issues: #4212, #1946; prerequisite for E1 · Delivered by P1, P4

A second host trigger, fired after a feed refresh and before playback, that passes metadata only — no file descriptor: 

parcelable PluginItemRequest {
    String guid; String enclosureUrl; String feedUrl;
    String title; long durationMs; long pubDate;
    boolean hasChapters; boolean hasTranscript;
    Map extras;   // Podcasting 2.0 tags core parsed but does not consume
}

This is what makes plugins useful to the (many) users who stream rather than download, and it is strictly cheaper than the download trigger: a database lookup keyed by GUID or enclosure URL needs no audio at all. It also gives a natural place to refresh generated content when the publisher edits an episode, which is the whole of #4212.

Guard rails: the trigger must be batched and rate-limited per refresh, must respect the metered-network setting, and must never delay the refresh itself — plugin work happens after items are committed.

E4 — Discovery: search providers and add-podcast sources

Motivating issues: #3545, #4747, #7486, #6299 · Delivered by P7, P8

:net:discovery already has the right shape in process: PodcastSearcherRegistry holds a list of PodcastSearcher implementations (iTunes, Fyyd, Podcast Index) that CombinedSearcher fans out to. E4 mirrors that registry across the binder, which is the same trick PR #14 played with MediaProcessorRegistry. 

interface IPodcastSearchPlugin {
    String getDisplayName();
    List<PluginSearchResult> search(String query, int limit);
    List<PluginSearchResult> searchEpisodes(String query, int limit);   // #7486
}
CAPABILITY_PODCAST_SEARCH = 1 << 4;
CAPABILITY_EPISODE_SEARCH = 1 << 5;
CAPABILITY_FEED_SOURCE    = 1 << 6;   // contributes an "add podcast" action

CAPABILITY_FEED_SOURCE is the smaller and more interesting half: a plugin contributes a labelled entry to the add-podcast screen that launches its own activity and returns a feed URL. That is exactly #3545 (QR scanning) — a feature whose real cost to core is a camera permission and a barcode dependency in the APK, both of which move to the plugin. NFC, clipboard watchers, and directory imports arrive for free.

New requirement: a small UI contribution API (label, icon, activity intent) that :ui:discovery renders. Keep it declarative — plugins supply data and an intent, never views.

E5 — Playback route / remote renderer hard

Motivating issue: #2920 · Delivered by P6

A plugin advertises playback devices and takes over transport; core keeps queue, position, and progress state. The in-process seam already exists and is proven: :playback:cast supplies a Chromecast PlaybackServiceMediaPlayer for the Play flavour, so a RemotePlaybackServiceMediaPlayer backed by a plugin is the same substitution with a binder in the middle. 

interface IPlaybackRoutePlugin {
    List<PluginRoute> getRoutes();
    boolean selectRoute(String routeId);
    void load(String mediaUrl, long positionMs, float speed);
    void play(); void pause(); void seekTo(long positionMs); void setVolume(float v);
    void setListener(in IPlaybackRouteListener listener);   // position + state callbacks
}
CAPABILITY_PLAYBACK_ROUTE = 1 << 7;

Ranked last on effort, first on structural payoff: it is the only proposal here that could eventually let Chromecast leave the Play-only flavour, replacing a build-flavour fork with an optional install. Sonos, UPnP/DLNA, and Snapcast then stop being upstream feature requests at all.

Caveats: remote devices need a reachable URL, so local files require the plugin to serve them; position reporting must be throttled hard; and a route disappearing mid-episode must fall back to local playback without losing position.

E6 — Sync and backup providers

Motivating issues: #1899, #4089; helps #6036 · Delivered by P9

:net:sync:service-interface already isolates SynchronizationProvider from its implementations — the module split AntennaPod uses for exactly this purpose. Exposing it over the binder lets alternative back-ends (WebDAV, a Drive folder, a Syncthing directory, a self-hosted endpoint) ship as plugin apps instead of as flavour-specific code or upstream feature requests. 

interface ISyncProviderPlugin {
    String getDisplayName();
    PluginSubscriptionChanges getSubscriptionChanges(long lastSync);
    PluginUploadResponse uploadSubscriptionChanges(in List<String> added, in List<String> removed);
    PluginEpisodeActionChanges getEpisodeActionChanges(long lastSync);
    void uploadEpisodeActions(in List<PluginEpisodeAction> actions);
}
CAPABILITY_SYNC_PROVIDER = 1 << 8;
CAPABILITY_BACKUP        = 1 << 9;   // exchanges an opaque blob from :storage:importexport

CAPABILITY_BACKUP is the cheaper half: core hands over the archive DatabaseExporter in :storage:importexport already produces, and the plugin decides where it goes. Note what is already in core — OpmlBackupAgent is registered as the app's android:backupAgent, so subscriptions do ride Android's Auto Backup today. What #1899 and #4089 still want is settings in the payload and destinations that are not Google's — the first is a core decision, the second is exactly what a plugin is for.

The same split governs sync: where data goes is plugin territory; what is in the payload (#6036 wants queue order) stays a core data-model decision.

E7 — Episode and feed actions

Motivating issue: #4671 · Delivered by P2

A plugin contributes a labelled action to the episode context menu, player screen, or feed screen, and receives the item's metadata — including Podcasting 2.0 tags that :parser:feed parses but core does not consume. 

interface IEpisodeActionPlugin {
    List<PluginAction> getActions(in PluginItemRequest item);  // id, label, icon, enabled
    void invoke(String actionId, in PluginItemRequest item);    // may start its own activity
}
CAPABILITY_EPISODE_ACTION = 1 << 10;

For #4671 this is what turns "become a Lightning wallet" into "core forwards a tag it already parsed". Core's entire share of the work is: retain podcast:value in extras, and render a "Boost" action supplied by a plugin. No wallet, no keys, no funds, no crypto dependency in the APK, and no exposure for users who never install it.

Prerequisite: PodcastIndex.java in :parser:feed handles funding, chapters, socialInteract, and transcript, and silently drops every other element in the namespace — value included. It needs to retain unhandled Podcasting 2.0 tags in a generic extras map instead.

E8 — Playback observer privacy-sensitive

Motivating issue: #4671 (streaming payments) · Delivered by P2

Coarse, throttled, one-way playback events for plugins that must react to listening rather than to downloads: 

oneway interface IPlaybackObserverPlugin {
    void onPlaybackEvent(in PluginPlaybackEvent event);   // STARTED | PAUSED | TICK | COMPLETED
}
CAPABILITY_PLAYBACK_OBSERVER = 1 << 11;   // tick interval >= 60s, host-controlled
This is the single most invasive capability proposed here: a continuous record of what the user listens to, delivered to another app. It must never be enabled by capability alone. Require a separate toggle with an explicit warning, deliver events only while playback is in the foreground service, coarsen positions, and never send them for episodes the user has marked private. If that bar is too high for a given use case, that use case does not get this capability.

7. What must stay in core

The most valuable thing this document can do is say no. Four clusters account for most of the Core verdicts above, and none of them should get an extension point:

Queue, inbox, and auto-download policy

#1077, #2648, #2077, #6671, #6158, #307, #2437, #4345

Tempting, because AutomaticDownloadAlgorithm and EpisodeCleanupAlgorithm are already swappable strategies. Resist it. These issues are not blocked on implementation — they are blocked on deciding what the app should do, and #1077's 133 comments are that argument, not a request for an API. A plugin point would export the disagreement to third parties and leave every user with a differently behaving queue.

The audio path

#4229, #8078, the real-time half of #2187

Continuous sample processing across a process boundary cannot meet latency or battery budgets. Core keeps the ExoPlayer AudioProcessor chain; plugins may only supply parameters for it (E2).

UI, layout, and theming

#7062, #6663, #6318, #7329

Plugin UI stays declarative: a label, an icon, an intent (E4, E7). Remote views or injected layouts would make accessibility, theming, and translation unownable.

Anything that must not be bypassable

#8191 (parental controls), #5237 (episode statuses)

A restriction enforced by an app the user can uninstall is not a restriction. And episode status is the vocabulary the rest of the app is written in; changing it is a core refactor by definition.

8. Sequencing

  1. Phase 0 — harden the contract (E0). Async results, payloads over an FD, contract versioning, provenance, declared side effects. Cheap now, expensive once plugins exist in the wild. Nothing below should land before this.
  2. Phase 1 — the flagship (E3 → E1 → P1). Metadata-time trigger first (it is small and independently useful), then segments, then the ad-skip plugin. Delivers the single most-wanted feature the plugin system can legitimately claim, and lands the shared segment model that #5924 also needs.
  3. Phase 2 — breadth on existing pipelines (E2, E4). Loudness analysis and discovery providers. Both reuse machinery that already exists (ExoPlayer volume, PodcastSearcherRegistry) and prove the model beyond post-download processing. Ships P3, P7, P8.
  4. Phase 3 — data ownership (E6, E7, E8). Backup/sync providers, episode actions, and — only with the consent design in E8 settled — the playback observer. Ships P9 and P2.
  5. Phase 4 — playback routes (E5, P6). Largest surface and the only one that touches the player's core state machine. Worth doing last and worth doing: it is the phase that turns a build flavour into an install choice.
One rule across all phases. Core never gains a dependency because a plugin wants one, and a user who installs no plugins must see no new permission, no new network traffic, and no new setting beyond the existing Settings → Plugins screen. Every entry point above is designed so that the default configuration of AntennaPod is byte-for-byte the app it is today.
