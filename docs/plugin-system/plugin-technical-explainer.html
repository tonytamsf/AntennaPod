Plugin Architecture for Engineers

A technical walkthrough of how AntennaPod runs third-party plugins as separate processes over Android IPC. Written for engineers who know systems but not necessarily Android.

The core problem

AntennaPod wants third-party plugins to process downloaded podcast audio — generating transcripts, chapter markers, or retention rules. The constraints:

  • No dynamic code loading. Google Play prohibits apps from downloading and executing code. So plugins can't be JARs, DEX files, or WASM blobs loaded at runtime.
  • Process isolation. A buggy plugin must not crash the podcast player.
  • Least-privilege. A plugin should see exactly one audio file, never the app's database or user data.
  • On-device only. No cloud uploads. AntennaPod is privacy-first FOSS.

The solution: each plugin is a separate Android app (its own APK, own process). The host app discovers them on the device and communicates over Android's built-in IPC mechanism.

The process boundary

The most important thing to understand: the plugin code never runs inside AntennaPod's process. The two apps communicate over Android's "Binder" IPC — think of it as a local RPC channel built into the OS kernel, similar to Unix domain sockets but with typed interfaces and OS-managed lifecycle.

Android-specific concept: AIDL. AIDL (Android Interface Definition Language) is Android's IDL for defining typed IPC interfaces. You write a .aidl file describing methods and data types; the build generates stub/proxy classes that serialize calls across the process boundary over the kernel's Binder driver. Think of it as gRPC but local-only and built into the OS.

The adapter seam

The download pipeline has zero awareness of plugins, IPC, or processes. It calls a simple in-process interface:

interface DownloadedMediaProcessor {
    String getId();
    boolean shouldProcess(FeedMedia media);
    void process(Context context, FeedMedia media);
}

RemoteMediaProcessor implements this interface and encapsulates all the cross-process complexity: binding the remote service, marshalling the request, handling timeouts, applying results. This is a textbook Adapter pattern — the seam where the rest of the codebase ends and the plugin world begins.

The 15-second timeout. RemoteMediaProcessor uses a CountDownLatch with a 15-second deadline when binding. If the plugin doesn't connect in time, the processor moves on. A hung plugin can't block the download pipeline indefinitely.

Discovery: how plugins are found

Each plugin's Android manifest declares a <service> with an intent-filter for the plugin action, plus <meta-data> carrying its plugin ID and a capability bitmask. This is how AntennaPod knows what the plugin can do before binding it.

Android-specific concept: <queries>. Starting with Android 11, an app can't see other installed packages by default (package visibility filtering). The host must declare a <queries> block listing the intent actions it wants to discover. Without this, queryIntentServices() returns an empty list even if plugins are installed.

What crosses the wire

The IPC contract is intentionally narrow. Two data structures cross the process boundary:

PluginMediaRequest →

capability — which single capability to invoke
mediaFd — a read-only file descriptor for the audio
mimeType, episodeTitle, durationMs

← PluginMediaResult

success, resultType (NONE / TRANSCRIPT / CHAPTERS)
content + contentMimeType — transcript text
chapters — list of PluginChapter (startMs, title, url, imageUrl)

Why a file descriptor, not bytes? Android's Binder has a ~1 MB transaction size limit. A podcast episode can be hundreds of megabytes. By passing a ParcelFileDescriptor opened read-only, the plugin gets a kernel-level handle to the file without any data being copied through the Binder buffer. The plugin can read/seek the audio file directly, the host controls access (read-only, single file), and the Binder stays within its limits.

Both structures are Parcelable — Android's serialization protocol for crossing process boundaries. Think of it as Protocol Buffers built into the framework: fields are written to and read from a Parcel in strict order, and the build tools generate the serialization code from the AIDL definitions.

The dependency direction means the download pipeline (:net:download:service) only depends on :plugin:api — it has no transitive dependency on AIDL, Binder, or any IPC machinery. You could swap out the entire host implementation without touching the pipeline.

Why AIDL over the alternatives

The team evaluated seven architectures. The two non-negotiable constraints — Play Store compliance (no dynamic code loading) and privacy (no cloud uploads) — eliminate the two simplest options immediately. Of what remains, only AIDL bound services model "process this file and return structured data" natively:

  • Broadcasts — no clean synchronous response path; modern Android restricts implicit broadcasts in the background.
  • ContentProviders — CRUD semantics are a poor fit for "process and return"; capability discovery must be bolted on.
  • WASM/scripting sandbox — large engineering effort; grey area on Play policy; hard to access native audio/ML libraries.
  • Bundled Gradle modules — simplest, but not a third-party ecosystem. Every plugin requires an AntennaPod release.

AIDL hits every requirement: typed process(request) → result semantics, real process isolation, file-descriptor handoff that respects the binder size limit, and plugins that ship and update as ordinary Android apps. The cost — AIDL boilerplate and a binding lifecycle — is fully contained behind the one-method DownloadedMediaProcessor seam.
